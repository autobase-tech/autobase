# Ansible Role: secrets

Stores Autobase values in an external secrets provider. The role is disabled when `secrets_provider` is empty and can be used for both cloud-provisioned and user-provided machines.

## Common variables

| Variable | Default | Description |
|---|---|---|
| `secrets_provider` | `""` | Secrets provider. Supported value: `aws`. An empty value disables synchronization. |
| `secrets_prefix` | `autobase/{{ patroni_cluster_name }}` | Prefix added to every secret name, except PostgreSQL users with their [own secret](#postgresql-users-with-their-own-secret) and names given as an [ARN](#secrets-in-another-aws-account). |
| `secrets_values` | `[]` | Arbitrary secrets. Each item requires `name` and, for `state: present`, `value`. Optional keys: `state`, `description`, and, for [value-only mode](#value-only-mode), `value_only`, `merge`, and `replace_non_object`. The `secret` key is reserved and rejected. |
| `secrets_export_postgresql_users` | `false` | Store successfully applied PostgreSQL user passwords in the selected format. |
| `secrets_export_connection_info` | `false` | Store connection addresses and ports generated by `deploy_finish`, without usernames or passwords. |
| `secrets_postgresql_users_path` | `postgresql/users` | Relative path for exported users; the username is appended. Not used for users with their own `secret`. |
| `secrets_postgresql_users_format` | `json` | Export `username` and `password` as JSON, or use `string` to export only the password. |
| `secrets_connection_info_path` | `postgresql/connection` | Relative name of the connection info secret. |

## AWS Secrets Manager variables

| Variable | Default | Description |
|---|---|---|
| `secrets_aws_region` | `server_location` when available | AWS region containing the secrets. Required for AWS. |
| `secrets_aws_kms_key_id` | `""` | Optional KMS key ID or alias. |
| `secrets_aws_recovery_window` | `30` | Recovery window used only for explicit deletion. Use `0` for immediate deletion or `7` through `30`. |
| `secrets_aws_manage_tags` | `true` | Manage tags on AWS secrets. Set to `false` to disable tagging completely. |
| `secrets_aws_tags` | `cloud_provider_tags` | Tags applied to AWS secrets. The role adds the `Cluster` tag when `secrets_aws_manage_tags` is enabled. |
| `secrets_aws_overwrite` | `true` | Update an existing secret with the same name. |
| `secrets_aws_value_only` | `false` | Only update values of existing secrets. See [Value-only mode](#value-only-mode). |
| `secrets_aws_value_compare` | `true` | In value-only mode, read the current value and write only when it differs. Set to `false` when `GetSecretValue` is not permitted. |
| `secrets_aws_resource_policy` | `null` | Optional resource policy, for example for cross-account access. |
| `secrets_aws_replica` | `null` | Optional list of replica regions and their KMS keys. |
| `secrets_aws_rotation_lambda` | `""` | Optional ARN of the Lambda function used for automatic rotation. |
| `secrets_aws_rotation_interval` | `null` | Optional number of days between automatic rotations. |
| `secrets_aws_secret_type` | `string` | Secret type: `string` or `binary`. Merging in [value-only mode](#value-only-mode) requires `string`. |
| `secrets_aws_endpoint_url` | `""` | Optional custom AWS API endpoint URL. |
| `secrets_aws_ca_bundle` | `""` | Optional path to a CA bundle used to validate AWS API certificates. |
| `secrets_aws_config` | `null` | Optional botocore configuration dictionary. |
| `secrets_aws_validate_certs` | `true` | Validate TLS certificates when connecting to the AWS API. |
| `secrets_aws_debug_botocore_endpoint_logs` | `null` | Optional botocore endpoint call logging switch. |

Secrets are created or updated by default. They are deleted only when `state: absent` is set explicitly. Removing an item from configuration does not delete it.

Secret names must be unique across `secrets_values`, exported PostgreSQL users, and the automatically exported `postgresql/connection` value. Duplicate names are not rejected: they are written in order, so the last value wins, and different values for the same name cause an update on every run. In [value-only mode](#value-only-mode), two exceptions write several values to one secret on purpose:

- Users and connection info can share one secret, see [PostgreSQL users and connection info in value-only mode](#postgresql-users-and-connection-info-in-value-only-mode).
- A `secrets_values` entry with `merge: true` adds its keys to a secret that Autobase also writes, for example the connection info secret.

The own `secret` of a PostgreSQL user is checked: the run fails if it matches another user's secret or any other secret written in the run.

The automatically exported `postgresql/connection` secret contains only connection endpoints. Export is skipped when connection information is unavailable or contains `N/A`, preserving any existing secret. Store credentials separately through `secrets_values`, for example as `postgresql/superuser`, when required.

```yaml
secrets_provider: aws
secrets_aws_region: us-west-2

secrets_values:
  - name: integrations/api-token
    value: "{{ integration_api_token }}"
  - name: applications/backend
    value:
      username: backend
      password: "{{ backend_password }}"
  - name: integrations/obsolete-token
    state: absent

secrets_export_postgresql_users: true
secrets_export_connection_info: true
```

AWS operations run on the Ansible controller and require `boto3` and `botocore`. By default, the role reads credentials from the controller environment:

```bash
export AWS_ACCESS_KEY_ID="..."
export AWS_SECRET_ACCESS_KEY="..."
```

Required permissions depend on the settings used. For value-only mode, see [its permissions](#value-only-mode).

| Permissions | When required |
|---|---|
| `secretsmanager:DescribeSecret`, `secretsmanager:GetSecretValue`, `secretsmanager:GetResourcePolicy` | Always. Existing secrets and their resource policy are read on every run. |
| `secretsmanager:CreateSecret`, `secretsmanager:UpdateSecret` | Always. Create missing secrets and update changed values. |
| `secretsmanager:TagResource` | `secrets_aws_manage_tags: true` (default), including tags set on creation. |
| `secretsmanager:PutResourcePolicy`, `secretsmanager:DeleteResourcePolicy` | `secrets_aws_resource_policy` is set, or an existing secret has a policy that must be removed. |
| `secretsmanager:RotateSecret`, `secretsmanager:CancelRotateSecret` | `secrets_aws_rotation_lambda` is set, or rotation must be disabled on an existing secret. |
| `secretsmanager:ReplicateSecretToRegions`, `secretsmanager:RemoveRegionsFromReplication` | `secrets_aws_replica` is set. |
| `secretsmanager:DeleteSecret`, `secretsmanager:RestoreSecret` | A secret has `state: absent`, or a secret scheduled for deletion is set to `present` again. |
| `kms:Decrypt`, `kms:GenerateDataKey` | `secrets_aws_kms_key_id` is a customer managed KMS key, including keys of replica regions. |

Note: when a secret already has a resource policy and `secrets_aws_resource_policy` is not set, the module removes that policy. Use [value-only mode](#value-only-mode) for secrets whose policy is managed elsewhere.

Secret values and module results are protected with `no_log`, and diff output is disabled.

## Secret names and paths

The final secret name is `<secrets_prefix>/<relative name>`. The exceptions are a PostgreSQL user with its [own secret](#postgresql-users-with-their-own-secret) and a name given as an [ARN](#secrets-in-another-aws-account), which are used as is. With the default prefix and `patroni_cluster_name: postgres-cluster-01`, the names are:

| Source | Relative name | Full secret name |
|---|---|---|
| A PostgreSQL user named `app_user` with `secrets_export_postgresql_users: true` | `postgresql/users/app_user` | `autobase/postgres-cluster-01/postgresql/users/app_user` |
| A PostgreSQL user with `secret: /backend/production/app-db` | — (full name, without the prefix) | `/backend/production/app-db` |
| Connection info with `secrets_export_connection_info: true` | `postgresql/connection` | `autobase/postgres-cluster-01/postgresql/connection` |
| A `secrets_values` entry with `name: integrations/api-token` | `integrations/api-token` | `autobase/postgres-cluster-01/integrations/api-token` |

- Each exported PostgreSQL user has a separate secret (in [value-only mode](#postgresql-users-and-connection-info-in-value-only-mode), all users without their [own secret](#postgresql-users-with-their-own-secret) share one secret). By default, it contains JSON with `username` and `password`; set `secrets_postgresql_users_format: string` to store only the password as a string.
- Password generation is disabled by default. With `postgresql_users_password_generation: on_create`, a new user with an empty, missing, or null password receives a generated 32-character password unless the user has `NOLOGIN`. When PostgreSQL user export is enabled, that password is stored in the configured secrets provider. Existing users with an empty password are left unchanged and their secrets are not overwritten. The `always` mode intentionally rotates and exports passwords on every run.
- Connection info is stored as one JSON secret containing the available endpoints, ports, and connection strings.

Set `secrets_prefix` to change the prefix for all secrets, including automatic exports. PostgreSQL users with their own `secret` keep their names:

```yaml
secrets_prefix: "company/production/my_pgcluster"
# PostgreSQL user: company/production/my_pgcluster/postgresql/users/app_user
# Connection info: company/production/my_pgcluster/postgresql/connection
```

Override the automatic paths independently with:

```yaml
secrets_prefix: "my-project/my_pgcluster"
secrets_postgresql_users_path: "database/users"
secrets_connection_info_path: "database/endpoints"
# PostgreSQL user: my-project/my_pgcluster/database/users/app_user
# Connection info: my-project/my_pgcluster/database/endpoints
```

Both paths are relative to `secrets_prefix`. The username is appended to `secrets_postgresql_users_path`; `secrets_connection_info_path` names a single secret.

A leading slash in a relative name is ignored; only `secrets_prefix` decides whether the final name starts with `/`. AWS treats `/backend/production/autobase-db` and `backend/production/autobase-db` as different secrets:

| `secrets_prefix` | Relative name | Full secret name |
|---|---|---|
| `""` | `backend/production/autobase-db` or `/backend/production/autobase-db` | `backend/production/autobase-db` |
| `"/"` | `backend/production/autobase-db` or `/backend/production/autobase-db` | `/backend/production/autobase-db` |

Changing the prefix or a secret name creates a secret under the new name; it does not delete the old secret. Delete old secrets explicitly with `state: absent` using their original prefix and relative name.

### Secrets in another AWS account

AWS resolves a secret name only in the caller's own account, so a secret in another account must be referenced by its ARN. A name that starts with `arn:` is used as is, without `secrets_prefix`. This applies to `secrets_connection_info_path`, `secrets_postgresql_users_path` in [value-only mode](#value-only-mode), `secrets_values` entries, and a user's own `secret`:

```yaml
secrets_aws_value_only: true
secrets_connection_info_path: "arn:aws:secretsmanager:us-west-2:123456789012:secret:/backend/production/app-db"
secrets_postgresql_users_path: "arn:aws:secretsmanager:us-west-2:123456789012:secret:/backend/production/app-db"
```

- Use [value-only mode](#value-only-mode): Autobase does not create secrets in another account, it only writes the values of existing ones.
- The region in the ARN must match `secrets_aws_region`.
- The secret's resource policy must allow the caller `secretsmanager:DescribeSecret` and `secretsmanager:PutSecretValue`, and also `secretsmanager:GetSecretValue` when the current value is compared or merged, which is the default.
- If the secret is encrypted with a customer managed KMS key, both the key policy and the caller's IAM policy must allow `kms:GenerateDataKey` and `kms:Decrypt` on that key.

### PostgreSQL users with their own secret

Set `secret` on a `postgresql_users` entry to store that user in the named secret instead of `secrets_postgresql_users_path`. Unlike other names, `secret` is the full secret name: `secrets_prefix` is not added, the username is not appended, and a leading slash is kept. Other secrets still use `secrets_prefix`:

```yaml
secrets_export_postgresql_users: true
postgresql_users_password_generation: on_create # generate passwords for new users, so they can be exported

postgresql_users:
  - { name: "app_user", password: "", secret: "/backend/production/app-db" }
  - { name: "report_user", password: "", secret: "{{ secrets_prefix }}/reports/report-db" }
  - { name: "batch_user", password: "" }
# app_user:    /backend/production/app-db
# report_user: autobase/postgres-cluster-01/reports/report-db
# batch_user:  autobase/postgres-cluster-01/postgresql/users/batch_user
```

AWS treats `/backend/production/app-db` and `backend/production/app-db` as different secrets. The `{{ secrets_prefix }}/...` form joins the strings as written, so it matches other secret names only for a prefix without a trailing slash. With `secrets_prefix: ""` it gives `/reports/report-db`, and with `secrets_prefix: "/"` it gives `//reports/report-db`; write the full name instead.

- The secret content follows `secrets_postgresql_users_format` in both modes, including [value-only mode](#value-only-mode): the user is not added to the shared users secret, and the value of its own secret is replaced entirely.
- A secret is written only when the user's password is known in this run. Changing `secret` of an existing user with an empty password does not export the user to the new secret; set the password explicitly. Avoid `postgresql_users_password_generation: always` for this: it rotates the passwords of all users with an empty password, not only this one. The old secret is not deleted.
- Users with `state: absent` and their own secret are not removed from any secret.
- In value-only mode, a user that was stored in the shared users secret keeps its key there after it gets its own `secret`, and the key is no longer updated. Remove it from the shared secret manually.

### PostgreSQL users excluded from the export

Set `secret: false` on a `postgresql_users` entry to keep that user out of all secrets, for example a user whose password is shared by several clusters and must not reach the secrets of their applications. An empty or null `secret` still means that the user has no own secret:

```yaml
secrets_export_postgresql_users: true

postgresql_users:
  - { name: "app_user", password: "", secret: "/backend/production/app-db" }
  - { name: "migrator", password: "{{ migrator_password }}", secret: false }
# app_user: /backend/production/app-db
# migrator: not exported
```

- The user is not written to its own secret or to the shared users secret, and is not removed from them with `state: absent`.
- A user that was exported before keeps its secret, or its key in the shared users secret in value-only mode. Remove it manually.

## Secret content examples

For a PostgreSQL user named `app_user`, the secret `autobase/postgres-cluster-01/postgresql/users/app_user` contains:

```json
{
  "username": "app_user",
  "password": "example-password"
}
```

The password above is illustrative; the exported value is the password successfully applied from `postgresql_users`.

To store only the password for every exported user:

```yaml
secrets_export_postgresql_users: true
secrets_postgresql_users_format: string
```

The same secret then contains the raw string, without JSON wrapping:

```text
example-password
```

Changing the format updates the value at the same secret path when overwriting is enabled. This setting applies only to automatically exported PostgreSQL users; connection info and `secrets_values` retain their existing formats.

For a cluster with a virtual IP and a single connection port, `autobase/postgres-cluster-01/postgresql/connection` contains, for example:

```json
{
  "address": "10.0.0.100",
  "port": 5432
}
```

With cloud load balancers for primary and replica connections, the same secret can contain:

```json
{
  "address": {
    "primary": "primary-lb.example.com",
    "replica": "replica-lb.example.com"
  },
  "port": 5432
}
```

The connection structure depends on the cluster configuration. For example, HAProxy with a virtual IP uses a `port` object with separate primary and replica ports; direct PostgreSQL connections can also include `connection_string`. The top-level `superuser` and `password` fields are excluded, but connection strings retain their username when present.

For arbitrary `secrets_values`, the secret contains the specified `value`: a scalar is stored as a string, and a dictionary or list is stored as JSON.

## Value-only mode

Value-only mode is a separate mode of operation with its own rules. The sections above describe the default mode; the differences are listed below.

Use value-only mode when the secrets are created and configured by another tool, such as Terraform. Autobase then writes only the secret value with `PutSecretValue`:

```yaml
secrets_provider: aws
secrets_aws_value_only: true
```

In this mode Autobase:

- Writes the value only when it differs from the current one, unless `secrets_aws_value_compare: false` is set. JSON values are compared as data, so formatting differences do not create new versions.
- Fails if the secret does not exist or is scheduled for deletion. It never creates, restores, or deletes secrets, and `state: absent` is rejected.
- Never changes the description, KMS key, resource policy, rotation, replication, or tags. The corresponding `secrets_aws_*` settings are ignored for these secrets.
- Respects `secrets_aws_overwrite`: with `false`, a value is written only if the secret has no current value. This also stops later updates of exported users and connection info.

The mode can also be set for a single `secrets_values` entry with `value_only: true` or `value_only: false`, which overrides `secrets_aws_value_only`. Automatically exported PostgreSQL users and connection info follow `secrets_aws_value_only`.

In value-only mode, a `secrets_values` entry with a dictionary value can set `merge: true`. Its keys are then merged into the current value of the secret instead of replacing it, and keys set to `null` are removed. This adds keys to a secret that Autobase also writes, for example the connection info secret:

```yaml
secrets_aws_value_only: true
secrets_connection_info_path: "backend/production/autobase-db"
secrets_values:
  - name: backend/production/autobase-db
    value:
      sslmode: require
    merge: true
# The secret contains the "connection" key written by Autobase and "sslmode".
```

- Merging requires `secrets_aws_value_compare: true` and `secrets_aws_secret_type: string`. Pre-checks reject an entry that does not meet these conditions.
- The current value must be empty or a JSON object. Entries are written before the connection info, so on the first run a placeholder string set by Terraform is still in the secret. Set `replace_non_object: true` on the entry to replace such a value with a warning.

Required permissions in this mode:

| Permissions | When required |
|---|---|
| `secretsmanager:DescribeSecret` | Always. Check that the secret exists and whether it has a current value. |
| `secretsmanager:GetSecretValue` | `secrets_aws_value_compare: true` (default). Compare the current value with the new one. |
| `secretsmanager:PutSecretValue` | Always. Write the value when it differs. |
| `kms:GenerateDataKey` | The secret uses a customer managed KMS key. |
| `kms:Decrypt` | The secret uses a customer managed KMS key and `secrets_aws_value_compare: true`. |

Where `GetSecretValue` is not permitted, set `secrets_aws_value_compare: false`. The value is then written on every run without comparison: each run creates a new secret version and reports a change. With `secrets_aws_overwrite: false`, existing values are never replaced, so no comparison is needed and `GetSecretValue` is not used. Merged secrets always require comparison; see the conditions below.

### PostgreSQL users and connection info in value-only mode

All exported users, except users with their [own secret](#postgresql-users-with-their-own-secret), are stored in one secret named by `secrets_postgresql_users_path`, without the username appended, under the `users` key. `secrets_postgresql_users_format` is ignored for them.

The new data is merged into the current value of the secret instead of replacing it:

- Users whose password is known in this run are added or updated. Passwords of other users are kept, because a password is known only in the run where it is set or generated.
- Users with `state: absent` are removed from `users`, unless they have their own `secret`.
- Other keys of the secret, for example those added by Terraform, are kept.
- If the current value is not a JSON object, for example a placeholder string set by Terraform, it is replaced and the run shows a warning.

Merging requires reading the current value, so `secrets_aws_value_compare: false` is rejected when users are exported to the shared secret: when any `postgresql_users` entry has no own `secret` and no `secret: false`, or when the users path equals the connection info path and connection info is exported. The shared users secret also requires `secrets_aws_secret_type: string`. Users with their own secret are written without merging and work with `secrets_aws_value_compare: false`.

Create the users secret before adding users. Secrets are written after the users are created in PostgreSQL, so if the secret is missing, the run fails and a password generated in that run is lost; the user then needs a new password.

Merging reads and writes the whole secret. If two Autobase runs update the same secret at the same time, one of them may overwrite the changes of the other.

Connection info is stored under the `connection` key and merged into the current value of its secret:

- The `connection` object is replaced entirely when it changes, so keys removed from the cluster configuration are also removed from the secret.
- Other keys of the secret are kept, so the connection info secret can also hold other data about the database, for example keys added by Terraform or by a `secrets_values` entry with `merge: true`.
- If the current value is not a JSON object, for example a placeholder string set by Terraform, it is replaced and the run shows a warning.

Merging requires `secrets_aws_value_compare: true` and `secrets_aws_secret_type: string`. If either is not set, a connection info secret that is not shared with users is written without merging: its whole value is replaced, and other keys stored in it are removed. A secret shared with users is always merged, so it requires both settings.

Autobase updates only the `connection` and `users` keys and never removes other keys from a merged secret. For example, if the users path no longer equals the connection info path, the old `users` key stays in the connection info secret and is no longer updated; remove it manually.

Set the same path for users and connection info to store both in one secret:

```yaml
secrets_aws_value_only: true
secrets_prefix: "/" # secret names start with a slash; use "" for names without it
secrets_export_postgresql_users: true
secrets_export_connection_info: true
secrets_postgresql_users_path: "/backend/production/autobase-db"
secrets_connection_info_path: "/backend/production/autobase-db"
# Secret name: /backend/production/autobase-db
```

```json
{
  "connection": {
    "address": "10.0.0.100",
    "port": 5432
  },
  "users": {
    "app_user": "example-password",
    "report_user": "example-password"
  }
}
```

With separate paths, users are stored under the `users` key of their secret and connection info under the `connection` key of its own secret. Both secrets are merged, so other keys stored in them are kept. With `secrets_aws_value_compare: false`, the connection info secret is replaced entirely instead.
